# Паспорт объекта: извлечение данных из Word — дизайн MVP

Дата: 2026-08-07

## Цель

Локальное веб-приложение на Python: пользователь создаёт новый проект, загружает
Word-файлы проекта (Договор генерального подряда — ДГП, и Приложение №1 —
Техническое задание — ТЗ), и приложение автоматически извлекает из них 6 полей
"паспорта объекта", сохраняя результат в JSON. Поля, которые не удалось найти,
остаются пустыми и редактируются вручную на той же странице.

Это первый этап более крупного портала. Другие возможности (дополнительные
действия с проектом, работа с существующим Excel-реестром "ГП_НДС 22%.xlsx" и
т.п.) в этот этап не входят и не проектируются здесь.

## Пользователи и контекст

Внутренний инструмент для сотрудников АО "МР Групп", работающих с договорами
генподряда. Один пользователь за раз, работа локально (без выхода в интернет),
без сложной системы прав доступа — не проектируем авторизацию в этом этапе.

## Ограничения и уже принятые решения

- Документы разных проектов используют один и тот же шаблон МР Групп, но с
  вариациями формулировок и структуры между проектами.
- Извлечение данных работает **только на своей инфраструктуре** — никаких
  внешних облачных LLM/API. Для MVP используется разбор по правилам
  (регулярные выражения и структурный анализ .docx), без нейросетей.
- Заполнение полей — **полностью автоматическое, без шага подтверждения**.
  Если поле не найдено — оно остаётся `null` в JSON и явно помечается в
  интерфейсе как требующее заполнения вручную. Программа не "угадывает"
  значения.
- Хранение — **без базы данных**. Каждый проект — папка на диске с исходными
  файлами и файлом `passport.json`.
- Язык реализации — Python. Единственная внешняя зависимость — веб-фреймворк
  Flask (плюс Jinja2, который идёт с ним). Чтение .docx — через стандартную
  библиотеку (`zipfile` + `xml.etree.ElementTree`), без python-docx/pandoc —
  они не установлены в среде, а ручной разбор уже опробован на реальных
  файлах в ходе анализа.

## Архитектура

```
Браузер (localhost:5000)
   │
   ▼
Flask-приложение
   ├── веб-маршруты (создание проекта, список, страница проекта, ручная правка)
   ├── document_reader.py   — .docx → (текст по абзацам, таблицы)
   ├── extractors.py        — 6 функций, по одной на поле паспорта
   ├── passport.py          — сборка/сохранение/загрузка passport.json
   └── storage/
        └── projects/<slug>/
             ├── raw/<загруженные .docx>
             └── passport.json
```

## Компоненты

**document_reader.py**
Принимает путь к .docx, возвращает:
- список абзацев (простой текст, без разметки)
- список таблиц (каждая — список строк, каждая строка — список текстов ячеек)

Реализация — на основе уже проверенного вручную подхода: .docx это zip-архив,
внутри `word/document.xml`; параграфы — теги `<w:p>`, ячейки таблиц — `<w:tc>`
внутри `<w:tbl>`.

**extractors.py**
Одна функция на поле, каждая принимает разобранные документы и возвращает
значение или `None`:

| Функция | Поле | Источник | Способ поиска |
|---|---|---|---|
| `extract_general_contractor` | Генподрядчик | ДГП | фраза `...именуемое в дальнейшем «Генподрядчик»` → название организации перед ней |
| `extract_signing_year` | Год подписания договора | ДГП | явная дата подписания рядом с преамбулой ("г. Москва", дата); сохраняется год (например `"2025"`); если дата не найдена — `None` |
| `extract_building_class` | Класс здания | ДГП + ТЗ | это маркетинговая, не техническая категория — в изученных примерах не встречается вообще; функция ищет по ключевым словам ("класс" рядом с "бизнес/премиум/комфорт/элит"), в норме возвращает `None` |
| `extract_underground_area` | Площадь подземной части, м² (ТЭП) | ТЗ, таблица ТЭП | строка таблицы с меткой, содержащей "подземн" |
| `extract_aboveground_area` | Площадь надземной части, м² (ТЭП) | ТЗ, таблица ТЭП | строка таблицы с меткой, содержащей "надземн" |
| `extract_total_area` | Общая площадь, м² (ТЭП) | ТЗ, таблица ТЭП | строка таблицы с меткой "общая площадь"; если отсутствует — не вычисляется автоматически (сумма подземной+надземной не всегда корректна методологически) |

Известное ограничение, подтверждённое на реальном примере: таблица ТЭП в
изученном ТЗ содержит только "Жилую площадь" по корпусам и этажность, но не
явную "Площадь подземной/надземной/общей части" в требуемой формулировке — то
есть на части документов эти 3 поля останутся пустыми, даже если разбор
работает правильно. Это ожидаемое поведение MVP, не ошибка.

**passport.py**
```python
PASSPORT_FIELDS = [
    "project_name", "year_signed", "building_class",
    "general_contractor", "underground_area_sqm",
    "aboveground_area_sqm", "total_area_sqm",
]
```
Собирает словарь из `project_name` (введено пользователем при создании) +
результатов всех extractors, сохраняет как `passport.json` (через `json.dump`,
`ensure_ascii=False`, с отступами для читаемости человеком). При ручной правке
через веб-форму — просто перезаписывает соответствующий ключ и сохраняет файл
заново.

## JSON-схема паспорта

```json
{
  "project_name": "Проспект Мира",
  "year_signed": null,
  "building_class": null,
  "general_contractor": "ООО «АНТТЕК»",
  "underground_area_sqm": null,
  "aboveground_area_sqm": null,
  "total_area_sqm": null
}
```
Все значения площадей — числа (м²) или `null`. `year_signed` — строка с годом
(например `"2025"`) или `null`. Остальные — строка или `null`.

## Данные и веб-маршруты

| Маршрут | Действие |
|---|---|
| `GET /` | список существующих проектов (папок в `storage/projects/`) |
| `GET /projects/new` | форма: название проекта + загрузка 2 файлов (ДГП, ТЗ) |
| `POST /projects` | сохранить файлы → прочитать → извлечь → сохранить `passport.json` → редирект на страницу проекта |
| `GET /projects/<slug>` | показать паспорт: найденные поля обычным текстом, пустые — подсвечены и доступны для ввода |
| `POST /projects/<slug>` | сохранить введённые вручную значения в `passport.json` |

## Обработка ошибок

- Загружен файл не `.docx` → понятное сообщение, повторная загрузка.
- Файл повреждён / не читается как .docx (ошибка при разборе zip/xml) →
  сообщение об ошибке на странице, проект не создаётся до успешной загрузки.
- Поле не найдено при разборе — это штатный результат (`None`/пусто), не
  ошибка и не исключение.

## Тестирование

- Юнит-тесты для каждой функции из `extractors.py` на реальных файлах-примерах
  ("250204 ДГП_Пр_Мира.docx" и "Прил. 1. Техническое задание Проспект
  Мира.docx"), которые уже проверены в ходе анализа. Ожидаемые результаты по
  этим файлам:
  - `general_contractor` → `"ООО «АНТТЕК»"`
  - `building_class`, `underground_area_sqm`, `aboveground_area_sqm`,
    `total_area_sqm` → `None` (задокументированное ограничение примера)
  - `year_signed` → скорее всего `None` (в тексте нет явной даты подписания)
- Ручной сквозной тест: запустить `flask run`, создать проект через браузер,
  загрузить эти же 2 файла, убедиться что `passport.json` и страница проекта
  показывают то же самое, что и юнит-тесты.

## Вне рамок этого этапа

- Развёртывание на реальном сайте/сервере (сейчас — только localhost).
- Любые действия с проектом кроме создания и просмотра/правки паспорта.
- Перенос данных в существующий Excel-реестр "ГП_НДС 22%.xlsx" — явно не
  требуется (см. обсуждение в диалоге).
- Локальная LLM как резервный способ извлечения — возможное расширение, если
  правила на реальных проектах окажутся недостаточно надёжными; не входит в
  MVP.
- Авторизация/многопользовательский режим.
